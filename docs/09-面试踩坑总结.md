# 面试踩坑总结 — 学习笔记

## 技术选型踩坑

### AtomicDouble 不存在

Java 标准库没有 `AtomicDouble`，用 `AtomicLong` 定点存储：`cost * 10000`。

### replaceAll 不支持 lambda

`String.replaceAll(regex, Function)` 不存在，必须用 `Matcher.appendReplacement` 手动循环。

### ThreadLocal 在异步场景失效

`TaskConsumer` 用虚拟线程，不继承请求线程的 `TenantContext`。

## 架构设计踩坑

### 管道顺序

从便宜到贵：限流(AtomicInteger 纳秒级) → 注入检测(微秒级) → 路由(百微秒级) → 模型调用(百毫秒级)。被挡掉的不浪费。

### 缓存 key 设计

最早只有 query，后来发现问题。最终三元组：`query + modelId + kbVersion`。

### 重试策略

第一次设计依赖 Kafka 重投，评审后改为自己控制的 3 次重试 + DEAD 状态，防故障放大。

## 工程验证踩坑（2026-10-16 补充）

### 单测全绿，应用起不来

升级 Spring Boot 3.x → 4.1.1 后，`mvn test` 全绿、`mvn verify` 通过，
但 `mvn spring-boot:run` 直接 **APPLICATION FAILED TO START**。三个叠在一起的病因：

1. **`ModelRegistry` / `ModelRouter` 漏加 `@Component`**——被 `AiGatewayService`
   构造器注入却没有 Bean 定义；
2. **`resilience4j-spring-boot3` 不兼容 Boot 4**——它的 `SpringBoot3Verifier`
   自动配置见到 Boot 4.x 直接抛 `IncompatibleSpringBootVersionException`。
   而这个依赖源码里**零处使用**（限流是 `GatewayRateLimiter` 的 AtomicInteger 手写实现）；
3. **"冒烟测试"是假的**——`assertNotNull(new PlatformApplication())` 直接 new 启动类，
   **根本不加载 Spring 上下文**，装配错误一个都测不出来。

**修复与教训**：
- 补 `@Component`、删除未使用且破坏启动的依赖、把冒烟测试改成真正的
  `@SpringBootTest` 上下文加载（并点名关键 Bean）；
- **大版本升级后必须启动一次应用**——编译和单测都证明不了"装配得起来"；
- **没用的依赖照样能炸掉你的应用**（自动配置的副作用与用不用无关）；
- 防复发的最小成本手段：一个真实的上下文加载测试，比多写一百个单测都管用。

### 缓存键与执行模型不一致

缓存查询早期要求请求同时带 `modelId + kbVersion`，且键用请求里的 `modelId`。
实测两个问题：普通问答不带 `kbVersion` → **缓存永远命中不了**（第二次相同请求
`cacheHit=false`）；客户端传错模型名 → A 模型的答案被缓存到 B 模型名下。
修复：键统一用**路由后**的 `selectedModelId`，`kbVersion` 可空记 `"none"`，
查询与回写共用同一组键。修复后实测第二次请求 `cacheHit=true, costTokens=0`。

### README 示例与代码不一致

快速开始的 curl 用的是 `/api/v1/chat`（实际 `/api/ai/chat`）、token 用
`demo-token`（实际鉴权要求 `sk-` 前缀）。**跟文档操作必失败**——
文档的示例必须跑一遍再提交，否则比没有文档更糟。

## 面试高频问题

1. 多租户行级隔离安全风险：异步任务路径是盲区
2. AI 网关 vs 普通网关：代理 vs 编排
3. SSE 限流：按 token 速率而不是连接数
4. 模型路由策略取舍：成本/性能/质量三选一
5. 三级缓存失效：Embedding 不需要在知识库更新时清除
