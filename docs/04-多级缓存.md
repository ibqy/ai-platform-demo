# 多级缓存 — 学习笔记

## 为什么要做多级缓存

AI 中台的调用链很长：向量检索 → Rerank → LLM 推理，每一步都有延迟和成本。如果同一个问题短时间内被反复提问（比如客服场景下多个用户问同样的问题），每次都从头跑完整条链路就是浪费钱和算力。

核心目标：
- 减少重复的 LLM 调用（最贵的一步）
- 避免重复向量化同一段文本（Embedding 调用也要钱）
- 缓存 RAG 检索结果，跳过向量检索 + Rerank
- 知识库更新后旧缓存自动失效，不返回过时数据

## 三级缓存架构

| 缓存 | 类 | Key 设计 | 存储内容 | TTL |
|------|------|----------|----------|-----|
| LLM 回答 | `LlmCache` | query + modelId + kbVersion | 完整 response | 300s |
| Embedding | `EmbeddingCache` | text 原文 | float[] 向量 | 600s |
| RAG 检索 | `RagResultCache` | query + kbVersion | List\<String\> chunkIds | 300s |

三个缓存都是 `ConcurrentHashMap` + 手动 TTL 检查（读时懒过期），没有引入 Redis——因为这是单机中台，不是分布式集群。生产环境如果要多实例部署，换成 Redis + Lua 脚本做原子 TTL 即可，接口不变。

## LLM 回答缓存

`LlmCache` 是最上层的缓存，命中后直接返回结果，跳过整个管道后半段（路由、调用、计量）。

Key 设计三段式：`query|modelId|kbVersion`

为什么需要三个维度？
- 同一个 query，不同模型的回答可能不同（`gpt-4o` vs `qwen2.5`）
- 同一个 query + model，知识库版本不同，检索到的上下文不同，回答也不同
- 缺任何一个维度都可能返回错误的缓存结果

```java
private String buildKey(String query, String modelId, String kbVersion) {
    return query + "|" + modelId + "|" + kbVersion;
}

public String get(String query, String modelId, String kbVersion) {
    String key = buildKey(query, modelId, kbVersion);
    CacheEntry entry = cache.get(key);
    if (entry == null) return null;
    // 懒过期：读的时候才检查是否超时
    if (System.currentTimeMillis() - entry.cachedAtEpochMs > ttlSeconds * 1000L) {
        cache.remove(key);
        return null;
    }
    return entry.response;
}
```

缓存命中时，管道里直接返回，token 消耗记为 0：

```java
// AiGatewayService.process() 步骤 6
String cached = cache.get(maskedQuery, request.modelId, request.kbVersion);
if (cached != null) {
    quotaManager.recordUsage(tenantId, 0, 0);  // 缓存命中不计 token
    return AiGatewayResponse.ok(cached, request.modelId, 0, true);
}
```

## Embedding 缓存

`EmbeddingCache` 缓存文本的向量结果。RAG 流程中，用户 query 需要先做 Embedding 再去向量库里搜，而同一段文本反复向量化的成本不低。

Key 直接用原文，不加其他维度——因为同一段文本的向量是确定性的（同一个模型输出固定），不需要区分模型或版本。

```java
public float[] get(String text) {
    CacheEntry entry = cache.get(text);
    if (entry == null) return null;
    if (System.currentTimeMillis() - entry.cachedAtEpochMs > ttlSeconds * 1000L) {
        cache.remove(key);
        return null;
    }
    return entry.embedding;
}
```

注意 TTL 是 600 秒，比 LLM 缓存的 300 秒更长。为什么？因为向量是确定性输出，不会随时间变化（模型不变的前提下），多缓存一会没问题。而 LLM 的回答可能有随机性（temperature > 0），缓存太久用户会觉得"怎么每次回答都一样"。

**知识库更新时不需要清除 Embedding 缓存**——因为 Embedding 缓存的 key 是文本原文，跟知识库版本无关。文本的向量表示不会因为知识库更新而变化。

## RAG 检索结果缓存

`RagResultCache` 缓存向量检索 + Rerank 的结果（chunk ID 列表）。Key 是 `query|kbVersion`，不包含 modelId——因为检索结果跟 LLM 模型无关，只跟知识库内容有关。

```java
private String buildKey(String query, String kbVersion) {
    return query + "|" + kbVersion;
}

public List<String> get(String query, String kbVersion) {
    String key = buildKey(query, kbVersion);
    // ... 同样的懒过期逻辑
}
```

存储的是 `List<String> chunkIds`（检索到的文档片段 ID），不是完整文本内容——减少缓存内存占用，实际内容从知识库按需加载。

## 缓存失效策略

三种失效机制，优先级从高到低：

1. **TTL 过期**：读时懒检查，`System.currentTimeMillis() - cachedAtEpochMs > ttlSeconds * 1000L` 就删除
2. **知识库更新主动清除**：`evictByKb(kbVersion)` 遍历所有 key，删除以 `|kbVersion` 结尾的条目
3. **全量清空**：`EmbeddingCache.clear()` 仅在极端情况使用（如模型切换）

`evictByKb` 的实现是遍历整个 map，用 `endsWith(suffix)` 匹配：

```java
public void evictByKb(String kbVersion) {
    String suffix = "|" + kbVersion;
    Iterator<Map.Entry<String, CacheEntry>> it = cache.entrySet().iterator();
    while (it.hasNext()) {
        Map.Entry<String, CacheEntry> entry = it.next();
        if (entry.getKey().endsWith(suffix)) {
            it.remove();
        }
    }
}
```

这个操作是 O(n) 的，但因为缓存条目通常不会太多（万级以下），遍历一次耗时可接受。如果缓存规模很大，应该换成按 kbVersion 分桶（`Map<String, Map<String, CacheEntry>>`），清除时直接删整个子 map。

## 缓存 Key 与脱敏的配合

管道里步骤 5 做 PII 脱敏，步骤 6 才查缓存——缓存 key 用的是脱敏后的 query：

```java
// 步骤 5
String maskedQuery = piiMasker.mask(request.query);
// 步骤 6
String cached = cache.get(maskedQuery, request.modelId, request.kbVersion);
```

这意味着：两个用户问同样的问题但携带不同的手机号，脱敏后 query 相同，能命中同一个缓存。如果用原始 query 做 key，缓存命中率会大幅下降。

## 关键踩坑

### 懒过期的内存膨胀问题

当前实现是"读的时候才检查过期"，如果一个 key 写入后再也没被读取，它就永远不会被清除。低流量场景下缓存会慢慢积累过期条目。生产环境应该加一个定时任务（如 `@Scheduled(fixedRate = 60000)`）定期扫描清理。

### evictByKb 的遍历锁

`ConcurrentHashMap` 的 `entrySet().iterator()` 是弱一致性的，遍历期间不会有 ConcurrentModificationException，但也不会看到遍历期间的修改。如果遍历过程中有新的写入，新条目可能被漏掉。对于缓存失效来说这个行为是可接受的——新写入的条目属于新版本，不应该被清除。

### Embedding 缓存的内存占用

`float[]` 向量（如 1536 维）每个占 6KB 左右，如果缓存 10 万条就是 600MB。教学项目里量不大没问题，生产环境需要设置缓存上限（LRU 淘汰）或改用堆外内存。

### 缓存穿透

恶意用户可以故意发送大量不重复的 query，每次都 miss 缓存，直接打穿到 LLM 调用。防御方案：对缓存 miss 的 query 做布隆过滤器或短期空值缓存。

## 面试高频问题

1. **为什么用 ConcurrentHashMap 而不是 Caffeine/Guava Cache？**
   教学项目保持简单，手动实现 TTL 逻辑清晰易懂。生产环境推荐 Caffeine，它支持自动过期、LRU 淘汰、异步刷新，而且性能经过大量优化。

2. **LLM 缓存为什么 key 要包含 modelId？**
   同一个问题路由到不同模型，回答可能不同。如果 key 不含 modelId，换了模型却返回旧模型的回答，用户体验会非常混乱。

3. **Embedding 缓存为什么不需要随知识库更新而清除？**
   Embedding 是文本到向量的确定性映射，跟知识库内容无关。知识库更新影响的是检索结果（哪些向量被选中），而不是向量本身。

4. **懒过期 vs 定时清理，各有什么优缺点？**
   懒过期：实现简单，无后台线程，但过期条目可能长期占用内存。定时清理：及时释放内存，但需要额外线程，且清理频率需要权衡。生产环境通常两者结合。

5. **缓存击穿怎么处理？**
   热点 key 过期时大量并发请求同时 miss，会瞬间打穿到 LLM。解决方案：互斥锁（只让一个请求去调 LLM，其他等待）、逻辑过期（不设实际 TTL，由业务判断是否需要刷新）。
