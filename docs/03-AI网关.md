# AI 网关 — 学习笔记

## 和普通 API 网关的区别

AI 网关不是纯代理，而是一个**编排引擎**。普通 API 网关做的事情：鉴权、限流、路由、日志。AI 网关在这个基础上多了：Prompt 预处理、模型选择、模板渲染、结果后处理、成本计量、缓存策略。

打个比方：普通网关是快递分拣中心——验一下包裹、贴上标签、丢给下一站。AI 网关是中央厨房——进来的食材要先洗（脱敏）、切（分块）、配（模板渲染）、烹饪（模型调用）、装盘（输出过滤）、还要记账（计量）。

核心挑战：每一步都可能失败，但失败的成本不一样。限流失败只是挡掉一个请求，模型调用失败可是实实在在烧了 token。

## 管道设计：便宜的优先

管道有 14 步，顺序经过精心设计：

```
限流 → 租户配额 → JWT鉴权 → 注入检测 → PII脱敏 → 缓存 → 路由 → 白名单 → TPM → Prompt渲染 → LLM调用 → 输出过滤 → 计量 → 回写缓存
```

这个顺序的核心哲学：**被挡掉的请求不花一个 token 的钱**。

具体来说：

- **限流（AtomicInteger，纳秒级）**：还没进业务逻辑就拦住了，零成本
- **注入检测（微秒级）**：正则 + 关键词匹配，CPU 开销极小
- **模型路由（百微秒级）**：内存查找，无 IO
- **LLM 调用（百毫秒~秒级）**：真正的开销在这里

如果在 LLM 调用后才做限流或注入检测，被挡掉的请求已经烧了 token。所以管道必须从便宜到贵排列。

另一个隐含的设计：**缓存放在脱敏之后、路由之前**。原因：

1. 脱敏后的 query 作为缓存 key 是稳定一致的（同一个"张三"无论怎么写都变成`张*`）
2. 缓存命中直接跳过路由和 LLM 调用，省掉所有后续开销
3. 缓存不命中时才走路由 → LLM，结果回写缓存

## 三层限流

`GatewayRateLimiter` 实现两层限流：

| 层级 | 默认值 | 实现 |
|------|--------|------|
| 全局 | 1000 QPS | AtomicInteger 计数器，每分钟重置 |
| 租户级 | 100 QPS | 每个租户一个独立计数器 |

`Resilience4j` 提供第三层——针对下游模型的熔断。当某个模型连续失败超过阈值时，自动将路由标记为不可用，避免雪崩。

为什么需要三层？设想一个场景：大租户突发流量，如果只有全局限流，大租户可能挤占所有令牌，小租户一个请求都发不出去。租户级限流保证了"每个租户至少能发 N 个请求"的公平性。

## 管道编排实现

`AiGatewayService.process()` 是整个中台的入口。设计原则：

### 上下文传递

用 `AiGatewayRequest/Response` 做上下文承载，不依赖 ThreadLocal（异步场景下 ThreadLocal 会丢失）。

```java
AiGatewayRequest {
    token, tenantId, query, modelId,
    kbVersion, templateId, templateParams, estimatedTokens
}

AiGatewayResponse {
    result, modelId, costTokens, cacheHit, errorCode
}
```

每个步骤读取 request 的对应字段，写入 response 或直接返回 error。这种模式让管道可插拔：新增一个步骤只需在 process() 里加一行，不影响其他步骤。

### 错误提前返回

每一步失败都直接 `return AiGatewayResponse.error("xxx")`，不再继续后续步骤。这是经典的 fail-fast 模式。

好处：
- 拒绝请求不消耗模型 Token
- 错误码精确，排查方便
- 每个步骤可以独立单元测试

## 关键踩坑

### 注入检测在 PII 脱敏之前

顺序不能反。假设用户在 Prompt 里写了一段 JSON 指令（注入攻击），如果先脱敏了，恶意指令可能被部分破坏或被遗漏检测。必须先检测风险再看原始输入。

### 缓存 key 的 query 必须用脱敏后版本

之前踩过一个坑：缓存 key 用原始 query，结果`"张三的电话是13800138000"`和`"张三的电话是13800138001"`产生了两个缓存条目，但其实内容完全一样（脱敏后）。

### 每个步骤可单独测试

管道设计的另一个好处：`ContentSafetyFilter`、`PiiMasker`、`ModelRouter` 都可以独立注入做单元测试。不用启动整个 Spring 容器。

### SSE 流式场景的特殊处理

当前管道是面向同步调用的。如果是 SSE 流式场景，输出过滤和缓存回写要在流结束后执行，不能在 token 级别做。这部分在生产环境需要额外处理。

## 面试高频问题

1. **AI 网关和普通 API 网关有什么本质区别？**
   普通网关是 proxy，AI 网关是 orchestrator + proxy。多了一层 Prompt 处理、模型选择、成本控制。

2. **管道步骤为什么这个顺序？**
   从便宜到贵排列，让"该挡掉的请求"在到达 LLM 之前就被拦住。

3. **限流为什么需要三层？**
   全局保护整体、租户级保护公平、模型级保护下游。

4. **缓存为什么放在脱敏之后？**
   确保缓存 key 的稳定性，同一个语义的 query 每次都能命中。
