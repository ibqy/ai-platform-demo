# 可观测与计量 — 学习笔记

## 为什么需要三层指标

一个 AI 中台的可观测不能只靠"请求量 + QPS"这种通用指标，还需要 AI 专属维度：
- 哪些租户在大量调用（成本归属）
- 哪个模型最受欢迎（选型依据）
- 哪些接口是瓶颈（性能优化方向）
- Token 消耗是否符合预算（成本控制）

## 三维指标体系

`PlatformMetrics` 基于 Micrometer 建立三个维度的指标，每个维度记录：
- `requestCount`：请求总量
- `successCount`：成功数
- `errorCount`：失败数
- `avgLatency`：平均延迟
- `p99Latency`：P99 延迟
- `totalTokens`：Token 总量

### 维度一：租户维度

tag: `tenant={tenantId}`

用途：
- 按租户计费
- 识别"羊毛党"租户（异常高频调用）
- 大租户资源规划

### 维度二：接口维度

tag: `endpoint={/api/v1/chat|/api/v1/embed|/api/v1/rerank}`

用途：
- 发现性能瓶颈接口
- 指导扩容方向
- 接口级告警

### 维度三：模型维度

tag: `model={gpt-4o-mini|qwen2.5-7b|...}`

用途：
- 模型使用率分析
- 成本优化（是不是太多人用了贵的模型？）
- 自动扩缩容模型实例

## Token 成本计量

`TokenMeter` 按租户 × 模型做成本记账：

```java
public class TokenMeter {
    // key: "tenantId:modelId", value: costMicro
    private final Map<String, AtomicLong> costMap = new ConcurrentHashMap<>();
    
    public void record(String tenantId, String modelId, int inputTokens, int outputTokens) {
        ModelMeta meta = registry.get(modelId);
        // 成本 = 输入token数 × 输入单价 + 输出token数 × 输出单价
        long cost = (long)(inputTokens * meta.getInputCostPer1k() / 1000.0 * 10000)
                  + (long)(outputTokens * meta.getOutputCostPer1k() / 1000.0 * 10000);
        costMap.computeIfAbsent(key, k -> new AtomicLong()).addAndGet(cost);
    }
}
```

### 定点数存储

用 `AtomicLong` 存 `costMicro`（成本 × 10000），规避 `AtomicDouble` 不存在的问题。精度到 0.0001 元，足够计费用。

```java
// 存储: costMicro = 1234  表示 0.1234 元
// 读取: actualCost = costMicro / 10000.0   → 0.1234
```

这是 Java 标准库的一个坑——有 `AtomicInteger`、`AtomicLong`、`AtomicBoolean`，偏偏没有 `AtomicDouble`。`DoubleAdder` 虽然存在但不是 `Atomic` 语义。

## 告警规则引擎

`AlertRules` 内置三条规则，每 30 秒检查一次：

### 规则 1：错误率告警

```java
if (errorRate > 0.20) {
    alert("租户 {} 错误率 {:.1%}，超过 20% 阈值", tenantId, errorRate);
}
```

注意这里用的是**租户维度**错误率，不是全局。因为全局错误率可能被个别租户拉高，但对其他租户没影响。

### 规则 2：Token 突增告警

```java
if (currentTokens > baseline * 1.5) {
    alert("租户 {} Token消耗突增 {:.0%}", tenantId, currentTokens / baseline - 1);
}
```

对比的是过去 5 分钟的均值，不是上一分钟。避免单个高峰误报。

### 规则 3：延迟告警

```java
if (p99Latency > 5000) {
    alert("模型 {} P99延迟 {}ms，超过 5000ms 阈值", modelId, p99Latency);
}
```

延迟检查在模型维度，因为不同模型的正常延迟范围不同（gpt-4o-mini 500ms，qwen2.5-72b 可能 3s）。

## 告警收敛

告警不是无限制发的。同一告警规则 5 分钟内只发一次：

```java
private final Map<String, Long> alertSuppress = new ConcurrentHashMap<>();

boolean shouldAlert(String alertKey) {
    long now = System.currentTimeMillis();
    Long last = alertSuppress.putIfAbsent(alertKey, now);
    if (last == null) return true;  // 第一次告警
    if (now - last > 300_000) {     // 超过5分钟
        alertSuppress.put(alertKey, now);
        return true;
    }
    return false;
}
```

## 关键踩坑

### min/max 初始值

延迟统计的 min 初始值要设为 `Long.MAX_VALUE`，max 初始值要设为 `Long.MIN_VALUE`。如果都用 0，第一次请求后 min 永远是 0，max 正确（因为延迟 > 0）。

```java
// ✅ 正确
long minLatency = Long.MAX_VALUE;
long maxLatency = Long.MIN_VALUE;

// ❌ 错误
long minLatency = 0;  // 永远等于0
long maxLatency = 0;  // 这个倒还好
```

### 定点存储精度

0.0001 元的精度够计费使用。但如果要对接财务系统（需要分/cents 级精度），需要乘 100000 而不是 10000。

### 告警阈值

硬编码的阈值（20% 错误率、50% 突增、5000ms 延迟）只是起点。成熟系统应该支持动态配置，甚至用 ML 做基线预测。

### Micrometer Tag 的基数爆炸

每个唯一 tag 值会创建一个独立的 Meter。如果租户数量是 10000，`tenant=tenant-0001` ~ `tenant=10000` 就会创建 10000 个 Meter，内存爆炸。生产环境需要用 `MeterFilter` 限制 tag 基数。

## 面试高频问题

1. **为什么没有 AtomicDouble？**
   Java 标准库的设计决策。`AtomicLong` 可以模拟定点数，`DoubleAdder` 提供累加但非 Atomic 语义。

2. **三层指标的用途分别是什么？**
   租户→计费与异常检测，接口→性能优化，模型→选型与成本控制。

3. **告警为什么需要收敛？**
   同一个问题可能触发大量告警，收敛防止告警风暴。

4. **Token 计量为什么放在管道最后一步之前？**
   放在 LLM 调用之后、缓存回写之前，确保只有真实调用才计费（缓存命中的跳过计量）。
