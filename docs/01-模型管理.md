# 模型管理层 — 学习笔记

## 为什么需要模型管理层

之前做 RAG 和 Agent 项目时，模型地址、API Key 都是硬编码在配置文件里的。换模型要改配置重启，模型挂了也没人知道。这次做中台，第一件事就是把模型抽象成**可管理的资源**。

核心需求：
- 多个模型动态注册/下线（不重启）
- 模型挂了自动探测，路由时跳过
- 根据场景智能选择模型（便宜 vs 快 vs 强）
- 支持 A/B 测试（灰度发布新模型）
- 按模型维度跟踪 TPM（Token Per Minute）配额

## 模型注册中心

核心是 `ModelRegistry`，一个线程安全的注册表。用 `ConcurrentHashMap` 存模型元数据，`ReentrantReadWriteLock` 控制并发——读多写少的场景，读写锁比 `synchronized` 高效得多。

`ModelMeta` 包含每个模型的关键信息：
- `modelId`：唯一标识（如 `gpt-4o-mini`, `qwen2.5-72b`）
- `type`：`CHAT` / `EMBEDDING` / `RERANK` / `MULTIMODAL`
- `apiEndpoint`：调用地址
- `costPer1kTokens`：输入/输出分别定价
- `avgLatency`：平均延迟（毫秒）
- `maxContextTokens`：上下文窗口大小
- `status`：`ONLINE` / `OFFLINE` / `UNSTABLE`
- `tags`：标签（如 `production`, `ab-test-v2`）

注册的模型分四类：
- `CHAT`：对话模型，最常用
- `EMBEDDING`：向量化模型，RAG 的基石
- `RERANK`：重排序模型，提升检索精度
- `MULTIMODAL`：多模态（图生文等），预留扩展

一个模型注册两种类型也是允许的（如 OpenAI 的 API 既是 CHAT 也是 EMBEDDING 的入口）。

## 健康探测

`ModelHealthChecker` 每 30 秒对所有已注册模型做一次健康检查。实现方式：

1. 对每个 ONLINE 状态的模型发一个最小化 ping 请求（如 "ping" 无上下文）
2. 设定超时阈值（5 秒），超时即标记异常
3. 连续 3 次失败 → 标记 UNSTABLE
4. 连续 3 次成功 → 恢复 ONLINE
5. UNSTABLE 状态下路由时降权（优先选 ONLINE 的）

为什么不直接标记 OFFLINE？瞬时网络抖动不应立即下线模型。连续失败才说明真的挂了。

## 智能路由策略

`ModelRouter` 实现了三种策略，通过 `RouteRequest.strategy` 指定：

| 策略 | 选型逻辑 | 适用场景 |
|------|----------|----------|
| COST | 选最便宜的可用模型 | 对质量不敏感的批量处理 |
| PERFORMANCE | 选延迟最低的 | 实时对话场景 |
| QUALITY | 选上下文窗口最大的 | 复杂推理任务 |

路由流程：
1. 从 `ModelRegistry` 获取指定类型的所有模型
2. 过滤掉 OFFLINE 和 UNSTABLE 的
3. 按策略排序：
   - COST：`inputCost + outputCost` 升序
   - PERFORMANCE：`avgLatency` 升序
   - QUALITY：`maxContextTokens` 降序
4. 返回第一个候选

## A/B 测试

`selectModelWithAB` 用租户 ID 的哈希值做灰度切流：

```java
int bucket = Math.abs(tenantId.hashCode()) % 100;
if (bucket < abPercent) {
    return experimentModel;  // 命中实验组
}
return controlModel;  // 对照组
```

同一个租户多次请求会稳定命中同一组——关键是不能让同一个用户一会走 A 一会走 B，那样体验割裂，数据也没法分析。

## TPM 配额管控

`ModelQuota` 按模型维度统计每分钟 token 消耗量：

- 使用滑动窗口计数器（每分钟一个桶）
- 超过 100000 TPM 的请求直接拒绝，返回 `tpm_exceeded`
- 这个限制部署在管道第 9 步（路由之后、LLM 调用之前）

为什么 TPM 放在路由之后？因为不同模型的 TPM 限制不同，需要先确定路由到哪个模型才能检查配额。

## 关键踩坑

### 路由和白名单的交互

管道里先路由再白名单校验（步骤 7→8），不是先过滤再路由。原因是：租户可能允许 5 个模型但不允许第 6 个，如果先过滤，路由就只能从 5 个里选；但先路由后校验，如果路由选中了不允许的模型就直接拒绝，保证逻辑清晰。

### 模型元数据热更新

`ModelMeta` 的 `avgLatency` 需要在每次调用后更新移动平均值。这里用了 `AtomicReference` + CAS 操作，避免对整个注册表加写锁。

### 健康探测的 "ping" 请求

不要用真实用户请求做健康探测。"ping" 无上下文、response 极短（几个 token），成本几乎为零。

## 面试高频问题

1. **模型路由选 COST/PERFORMANCE/QUALITY 的依据是什么？**
   根据业务场景：批量离线处理用 COST，实时对话用 PERFORMANCE，长文档分析用 QUALITY。

2. **A/B 测试怎么保证同一用户稳定命中同一个组？**
   租户 ID 哈希取模，不依赖外部存储。

3. **健康探测为什么是连续失败 3 次才标记？**
   防止瞬时网络抖动误判。生产环境常用"连续 N 次失败"来确认真的宕了。
