# 多租户架构 — 学习笔记

## 为什么需要多租户

企业级 AI 中台面对的不是单一用户，而是多个业务线/多个客户。每个租户有自己的：
- 调用配额（每日请求数、Token 上限）
- 模型白名单（只允许使用特定模型）
- 独立计费（成本分摊）

但作为中台，不能给每个租户部署一套独立服务——运维成本爆炸。

## 行级隔离 vs 独立实例

两种主流方案：

### 共享存储 + 行级隔离（本项目选的方案）

所有租户数据在一个 Redis/一个表里，每条数据绑 `tenant_id`。

- **优点**：成本低、运维简单、新租户秒级开通
- **缺点**：代码里处处带着租户过滤，异步场景容易遗漏
- **适用**：中小租户、SaaS 场景

### 独立实例隔离

每个租户独立 Redis/独立数据库/独立部署。

- **优点**：强隔离、大租户资源独享、安全合规
- **缺点**：成本高、运维复杂
- **适用**：大客户、金融/医疗等强合规场景

实际项目中通常是混合：中小租户用行级隔离，VIP 大客户走独立实例。

## TenantContext 设计

`TenantContext` 用 `ThreadLocal` 存当前租户信息：

```java
public class TenantContext {
    private static final ThreadLocal<String> tenantIdHolder = new ThreadLocal<>();
    private static final ThreadLocal<Tenant> tenantHolder = new ThreadLocal<>();

    public static void setTenant(Tenant tenant) {
        tenantIdHolder.set(tenant.getTenantId());
        tenantHolder.set(tenant);
    }

    public static String getTenantId() {
        return tenantIdHolder.get();
    }

    public static void clear() {
        tenantIdHolder.remove();
        tenantHolder.remove();
    }
}
```

生命周期：网关鉴权通过后 `GatewayAuthFilter` 塞入上下文 → 请求处理完毕 → 在 Filter 的 finally 块中 `clear()`。

**关键**：`finally` 里 `remove()` 是必须的。如果线程被线程池回收，ThreadLocal 残留会污染下一个请求——这就是经典的 ThreadLocal 内存泄漏。

## 模型白名单

`Tenant.modelWhitelist` 是最后一道防线——路由选出了模型后白名单校验：

```
路由选择 gpt-4o → 查白名单 → gpt-4o 在列表里吗？
                                     ├─ 是 → 放行
                                     └─ 否 → model_not_allowed
```

为什么放在路由之后而不是之前？
- 先路由再校验：路由从全部模型池中选最优
- 先过滤再路由：路由范围被缩小

显然后者更合理？不，实际需求是：租户可能有 A/B 测试需求（让 10% 流量走到实验模型），先过滤再路由会让 A/B 测试无法实现。所以设计是先路由选出最优模型，再用白名单做第二道拦截。

## 配额与欠费熔断

`TenantQuotaManager` 按租户维度跟踪每日用量：

```java
class TenantQuota {
    int maxRequests = 10000;      // 每日请求上限
    int maxTokens = 1000000;      // 每日 Token 上限
    AtomicInteger usedRequests;   // 已用请求数
    AtomicLong usedTokens;        // 已用 Token 数
    long lastResetTime;           // 上次重置时间戳
}
```

重置逻辑：每次 `checkQuota` 时检查 `lastResetTime` 是否跨日。如果跨日，重置所有计数器。

为什么不依赖外部定时任务？分布式场景下各实例时钟可能不一致，用自带的跨日检测更安全。

## 关键踩坑

### ThreadLocal 用完 `remove()` 防泄漏

线程池场景下线程不销毁，ThreadLocal 不清就会一直存着。Tomcat 默认线程池 200 个线程，每一个都可能残留。

### WebFlux 下 ThreadLocal 不生效

本项目用 Servlet 模型（Tomcat），一个请求一个线程，ThreadLocal 天然可用。如果切换到 WebFlux（Netty），一个请求可能在多个线程上执行，ThreadLocal 会丢失。WebFlux 下应该用 Reactor Context。

### 异步场景下租户 ID 必须显式传递

`TaskConsumer` 用虚拟线程（`Thread.startVirtualThread`），不继承请求线程的 ThreadLocal。所以 `TaskPublisher` 发布任务时必须把 `tenantId` 编入 `AsyncTask` 的 payload，消费者从 payload 中取值。

### 白名单和路由交互

上文已详述：先路由再校验。这里容易犯的错误是把白名单当成路由的前置过滤。

## 面试高频问题

1. **多租户行级隔离有什么安全风险？**
   异步任务路径是最大的盲区。异步消费者如果没有显式带上租户 ID，就可能用错误的租户上下文处理数据。

2. **怎么选择隔离方案？**
   看租户数量和规模。<100 个中小租户用行级隔离，>100 个或有大客户用混合方案。

3. **配额重置为什么不用定时任务？**
   分布式时钟不可靠，基于持久化时间戳 + 请求时检测更安全。
