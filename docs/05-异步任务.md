# 异步任务 — 学习笔记

## 为什么不能走同步

文档解析、批量向量化需要分钟级处理，HTTP 同步接口不可能等。核心思路：**提交即返回，后台慢慢跑，前端轮询状态**。

## 任务状态机

```
QUEUED → PROCESSING → SUCCEEDED
                    ↘ FAILED → RETRYING → QUEUED（重新入队）
                                       ↘ DEAD（达到 maxRetries）
```

`AsyncTask.TaskStatus` 定义了 7 种状态：`QUEUED / PROCESSING / SUCCEEDED / FAILED / RETRYING / DEAD / CANCELLED`。

关键设计：
- `RETRYING` 不是终态，把任务重新 `publish` 回队列尾，状态回到 `QUEUED`
- `DEAD` 是终态——失败次数达到 `maxRetries`（默认 3）后不再重试，避免故障放大
- 为什么 `DEAD` 而不是无限重试？失败三次后大概率是任务本身有问题（格式错误、资源不存在），继续重试浪费资源

## 五大核心类

**AsyncTask**：任务实体。`payload` 用 JSON 字符串而不是泛型对象，是为了后续对接真实 MQ 时序列化零成本。关键字段：`taskId`（UUID）、`type`、`payload`、`status`、`retryCount`、`maxRetries`、`progress`（0~100 进度条）。

**TaskPublisher**：用 `ConcurrentLinkedQueue<AsyncTask>` 模拟消息队列。无锁队列，`add`/`poll` 都是 CAS 操作，吞吐量远高于 `BlockingQueue`。生产替换为 Kafka 只需改这个类。

**TaskStore**：用 `ConcurrentHashMap<String, AsyncTask>` 模拟持久化。每次 `save` 自动更新 `updatedAtEpochMs`，前端轮询可以看到最新进度。支持 `listByStatus`、`listByType` 等筛选。

**TaskConsumer**：虚拟线程（Java 21）做消费循环，`@PostConstruct` 启动。

```java
Thread.ofVirtual().start(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        AsyncTask task = publisher.poll();
        if (task != null) {
            process(task);
        } else {
            Thread.sleep(1000);  // 队列空时休眠，避免空转
        }
    }
});
```

重试逻辑：失败后不原地等待，而是**重新入队尾**——让其他任务先执行，避免慢任务阻塞队列。

```java
} catch (Exception e) {
    task.setRetryCount(task.getRetryCount() + 1);
    if (task.getRetryCount() < task.getMaxRetries()) {
        task.setStatus(TaskStatus.RETRYING);
        publisher.publish(task.getType(), task.getPayload(), task.getMaxRetries());
    } else {
        task.setStatus(TaskStatus.DEAD);
    }
}
```

**TaskController**：三个 REST 端点。`POST /submit` 提交返回 taskId，`GET /{taskId}` 查状态，`GET /list` 按状态/类型筛选。

## 关键踩坑

### ThreadLocal 在虚拟线程里丢失

虚拟线程 I/O 阻塞时会被 unmount 到不同载体线程，`ThreadLocal` 里的租户 ID 丢了。**解决**：把上下文编入 `payload`，不从 `ThreadLocal` 取。

### 空转 CPU 飙高

队列空时不做休眠，`while` 循环纳秒级调 `poll()`，CPU 直接拉满。必须 `Thread.sleep` 或改用 `BlockingQueue.take()` 阻塞等待。

### DEAD 任务需要告警

`DEAD` 意味着彻底失败，生产环境必须接告警（钉钉/企微），否则任务悄悄死了没人知道。

### 任务持久化

当前内存实现重启会丢。生产方案：(1) MQ 持久化消息；(2) 提交时先写 DB 再入队；(3) 启动时扫描非终态任务重新入队。

## 面试高频问题

1. **为什么用 `ConcurrentLinkedQueue` 而不是 `ArrayBlockingQueue`？**
   无锁队列更简单，`poll()` 返回 null 配合 sleep 即可。生产用 `BlockingQueue.take()` 自动阻塞等待更优雅。

2. **虚拟线程和线程池怎么选？**
   虚拟线程适合 I/O 密集型（等 API 返回），线程池适合 CPU 密集型（向量计算、加密）。

3. **重试为什么重新入队而不是原地重试？**
   原地重试会占住消费线程，其他任务也无法处理。重新入队让失败任务排到队尾，不阻塞正常任务。

4. **怎么保证任务不丢失？**
   内存实现会丢。生产需要：MQ 持久化 + DB 兜底 + 启动时恢复非终态任务。
